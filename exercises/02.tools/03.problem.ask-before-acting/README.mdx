# 💪 Ask before acting

Your bot can search the catalog and move customers around the site. Both of those are safe — read-only or "just changes the URL". But the moment a tool *does something* on the customer's behalf — adding to cart, applying a discount, sending an email — you do not want the model just doing it. You want the customer to see what is about to happen and click Yes or No first.

In this exercise you'll build an `addToCart` client tool that **needs approval**. The model can pick it, but TanStack AI will pause and wait for the customer to confirm before the tool's code actually runs.

## 🐨 What you will do

Same three-piece shape as the last exercise — define the tool, register it on the server, build the client side — but with one new field on the definition and a new piece of UI for the approval prompt.

### 1. `app/tools/cart.ts` — define the tool

This new file already has the two schemas built for you (`AddToCartInput` and `AddToCartOutput`).

1. 🐨 At the bottom of the file there's a 🐨 block. Use it to build and export `addToCartDef` with `toolDefinition({...})`. Same pattern as `navigateToDef` from last time — but this one has one new field you've never used before: `needsApproval: true`. Setting that on the definition is what makes TanStack AI pause and wait for the customer to click Yes or No before running the tool. Marty 💰 hands you the `name` and the `description` string; plug in `AddToCartInput` and `AddToCartOutput` as the schemas.

### 2. `app/routes/api.chat.tsx` — tell the model the tool exists

2. 🐨 Add `addToCartDef` to the array inside `mergeAgentTools([...], clientTools)` on the `chat({...})` call. Same as last time — even though the tool runs in the browser, the server has to advertise it so the model knows it exists. It matters even more here: the browser's copy of the tool doesn't carry `needsApproval: true`, so only the server's copy makes the run stop for approval.
3. 💣 Delete the `void addToCartDef` line above the action.

### 3. `app/components/product-chat.tsx` — provide the implementation *and* the approval UI

This is where the new concept lives. You'll do three things here.

4. 🐨 Import `addToCartDef` from `#app/tools/cart.ts` once it exists (importing it before you've exported it breaks every page of the store). Then build the `addToCart` client tool with `addToCartDef.client(execute)`. The 🐨 block above the `useChat({...})` call walks you through it — same shape as the `navigateTo` tool just above, but the callback closes over `cart` (from `useCart()`) and calls the pre-built `addProductToCart(...)` helper to do the real work.
5. 🐨 Add `addToCart` to the `tools: [...]` array on `useChat({...})`.
6. 🐨 In the `switch (part.name)` further down, add `case 'addToCart'`. The 🐨 comment there lays out its three outcomes (added, waiting for approval, declined) and has the ready-made components for each: `<AddedToCartNotice />`, the `🛒 Add to cart?` card `<AddToCartApproval />`, and `<CancelledNotice />`. For the card, find this tool call's `approval` in `interrupts`, then wire **Yes** and **No** through its `onApprove` / `onDeny` props: call `approval.resolveInterrupt(true)` for Yes and `approval.resolveInterrupt(false)` for No.

## 🦉 How approvals work in TanStack AI

The flow looks like this:

1. Model decides to call `addToCart` with some args.
2. Because the tool's definition has `needsApproval: true`, TanStack AI **does not** run your `.client(...)` callback. The server stops the run with an **interrupt**: a decision that a person must make before the run can continue.
3. `useChat` puts that decision in `interrupts`. A tool approval has `kind: 'tool-approval'`, the `toolCallId` of its tool call, and the model's arguments in `originalArgs`.
4. Your UI finds the approval for the tool call, renders Yes/No buttons, and the customer clicks.
5. The click handler calls `approval.resolveInterrupt(true | false)`. `useChat` then sends a new request that continues the paused run.
6. If approved, **then** TanStack AI runs your `.client(...)` callback and the result goes back to the model.
7. If denied, the callback never runs. The model is told the request was rejected and can respond accordingly ("ok, I won't add it").

This separation — definition says "needs approval", the run pauses on an interrupt, your answer continues it — is the entire pattern. Once you've wired it once you can apply it to any "this tool *does something*" tool you build later.

🦉 "No" is not the same as "cancel". `resolveInterrupt(false)` is an answer: the run continues and the model sees the rejection. `approval.cancel()` drops the decision without an answer. For a Yes/No card, you want `resolveInterrupt`.

## 🦉 Why the approval prompt shows fields like `productName`

The model is the one filling in `productName`, `size`, `color`, and `quantity` — not your code. The approval prompt shows those back to the customer **before** anything runs, so they can see exactly what the model was about to do. If the model picked the wrong size, the customer rejects and the bot tries again.

This is why `productName` is in the tool's `inputSchema` even though the cart already has a name field internally — the schema is the *contract for what the model has to provide*, and we want it to provide a human-readable name so the approval card is readable.

## ✅ How to know it is working

Open the chat panel and try these:

- **On a product page, "Add this to my cart, size 10, in red"** → the bot picks the `addToCart` tool, the chat shows a Yes/No card with the product name and the size/color/qty, and *nothing actually happens to your cart yet*. Click **Yes** → the card is replaced with `✅ Added to your cart` and the cart count goes up. Click **No** → you see `❌ Cancelled — not added` and the cart is unchanged.
- **"Add the Air Zoom Pegasus 38 to my cart"** while on the home page → same flow. The bot can also reach for `searchProducts` first if it needs to look up the id.
- **Navigate to `/cart`** after a successful add → the item is in the cart, with the right size, color, and quantity.

## 🚨 If you get stuck

- **TypeScript complains that `addToCartDef` is not exported** → you haven't built it yet in `app/tools/cart.ts`. The 🐨 block there is the spec. Until it exists you'll also see the error in `tool-parts.tsx` and `api.chat.tsx`, which import it.
- **Every page of the store shows an error** → `product-chat.tsx` imports `addToCartDef` before `cart.ts` exports it. Build the definition first, then add the import.
- **The bot adds things to the cart with no prompt** → one of two things:
  - You forgot `needsApproval: true` on the tool definition. Without that field, the tool runs the moment the model picks it.
  - `addToCartDef` is missing from the server's `mergeAgentTools([...])` array. The server then only has the browser's copy, which doesn't carry `needsApproval`, so it never asks for approval and the browser runs the tool straight away. The console warns that the server and client tool schemas differ. This is why approval has to live in the server's copy of the tool.
- **The chat sits on `🔧 Calling addToCart…` and no card ever shows** → `addToCart` isn't in the `useChat({ tools: [...] })` array, so the browser has no tool to bind the approval to.
- **The Yes/No buttons render but clicking does nothing** → the `onApprove` / `onDeny` props on `<AddToCartApproval />` still have the `// 🐨` placeholders. Replace them with `approval.resolveInterrupt(true)` and `approval.resolveInterrupt(false)`.
- **TypeScript says `'addToCart'` is not comparable in the `switch`** → `addToCart` is not in the `useChat({ tools: [...] })` array yet. The message parts are typed from that array.
- **You see `✅ Added to your cart` but the cart is empty** → the `.client(...)` callback returned `{ added: true }` without actually calling `addProductToCart(...)`.
- **The model picks weird sizes/colors** → that's actually fine for this exercise — the approval prompt is the safety net. The customer rejects, and the model tries again. If you want better defaults, you could extend the system prompt to nudge the model toward common sizes.
